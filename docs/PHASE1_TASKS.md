# Phase 1 タスク指示書

Claude Code にそのまま渡すための作業指示。上から順に着手する。
**すべてのタスクで `implementer` → `reviewer` の相互レビューを回すこと**（`CLAUDE.md` 参照）。

---

## T0. 前提の確認（最初の1回だけ）

- [ ] `docs/DESIGN.md`（設計書）をリポジトリに配置し、内容を読む
- [ ] `CLAUDE.md` を読み、アーキテクチャの不変条件を把握する
- [ ] `.claude/agents/implementer.md` と `reviewer.md` が読み込まれていることを確認する
- [ ] `uv sync && uv run pytest` が通ることを確認する

---

## T1. Elo モジュールの取り込み ★着手済み・要レビュー

`core/elo.py` / `tests/test_elo.py` / `experiments/sim_elo.py` は実装・検証済み（48テスト通過）。

- [ ] 3ファイルをリポジトリに配置する
- [ ] **`reviewer` に第三者レビューさせる**（実装は別環境で行われたため、必ず通すこと）
- [ ] `docs/ELO_VERIFICATION.md` を配置する
- [ ] 旧 `core/difficulty.py` は削除せず残す（新旧比較の基準として使う）

**レビューで特に見てほしい点:**
- `select_item_index` の重み付き抽選で、`total <= 0` のフォールバック経路が正しいか
- `effective_result` の解答時間割引が、遅い正解を不正解より低く評価してしまわないか
- `THETA_MIN/MAX` のクランプが推定を歪めないか（真の能力が範囲外の生徒がいた場合）

---

## T2. 尺度のアンカリング方式を決める ★T3より先にやる

`docs/ELO_VERIFICATION.md` の「尺度のアンカリング」参照。theta と beta を同時更新すると
尺度全体がドリフトする。**後から直すと過去の theta が無意味になるため、DB を作る前に決める。**

- [ ] 方式を2案以上出して比較する
      (a) アンカー項目を固定して beta を更新対象から外す
      (b) 定期バッチで beta 平均を 0 に再センタリング
- [ ] シミュレーションで長期ドリフト（10万解答規模）を再現し、各案の効果を測る
- [ ] 決めた方式を `docs/ELO_VERIFICATION.md` に追記する
- [ ] `core/elo.py` に必要な関数を追加する（純関数のまま）

---

## T3. 解答形式の抽象化（`answer_type`）

旧版の `answer: int` 決め打ちを壊す。**ここを後回しにすると Phase 3 で全面書き直しになる。**

- [ ] `core/answers.py` を新設し、解答の表現と正誤判定を定義する
      `integer` / `fraction` / `decimal` / `choice` / `text` / `kanji`
- [ ] 正誤判定は形式ごとに異なる（分数は約分後に比較、小数は許容誤差、テキストは正規化）
- [ ] 「惜しい」判定を返せる設計にする（子どもへのフィードバックに使う）
- [ ] 全形式について境界値・異常系のテストを書く

---

## T4. ItemTemplate の抽象化

- [ ] `core/templates.py` を新設。`generate_problem(level, seed)` を
      `generate(template_id, seed) -> Item` に一般化する
- [ ] `Item` は「問題文・正解（`answer_type` 付き）・想定解答時間・所属KC」を持つ
- [ ] 決定論を維持する（同じ `(template_id, seed)` から常に同じ問題）
- [ ] 旧 `core/problems.py` の生成器を新形式のテンプレートとして移植する
- [ ] 全テンプレートについて「生成した問題の正解が実際に正しいか」を検算するテストを書く

---

## T5. 算数 KC ツリーとテンプレート定義

実装よりデータ整備の作業量が大きい。早めに着手する。

- [ ] 小3〜小6の KC ツリーを定義する（数と計算・図形・測定）
- [ ] 各 KC に 3〜5 個のテンプレートを割り当て、計 40〜60 個作る
- [ ] 各テンプレートに beta の初期値を人手で見積もる（T2 の結論に従う。0 で始めない）
- [ ] 各テンプレートに想定解答時間を設定する

---

## T6. FastAPI スケルトンと DB スキーマ

- [ ] `docs/DESIGN.md` §6 のデータモデルを SQLAlchemy で実装
- [ ] `Attempt` は追記のみ。更新・削除の経路を作らない
- [ ] 1セッション分の API（セッション開始 → 出題 → 解答 → 終了サマリ）
- [ ] 学習者は UUID 主キー。氏名は必須にしない

---

## T7. Next.js の子ども用 UI

- [ ] 1セッションを通しで動かす（ホーム → 出題 → 解答 → 終了サマリ）
- [ ] アプリ内テンキー（OS キーボードを使わない）
- [ ] 最小フォントサイズ 18px、ふりがな切替
- [ ] 問題表示は 100ms 以内（テンポが死ぬとfunモードの価値が消える）

---

## T8. 学童でのユーザーテスト

- [ ] 子ども3人に1週間使ってもらう
- [ ] 観察する指標: 着席までの時間、セッション完走率、2日目以降の再訪率
- [ ] **正答率は見ない**（目標75%に張り付くので情報がない）
