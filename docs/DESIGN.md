## 0. この文書の位置づけ

課題として提出した CLI 版 drillnavi を、**学童・塾・家庭に提供できる Web アプリ**へ作り替えるための設計書。
実装に入る前の合意形成用であり、決定事項は都度この文書を更新する。

決定済みの前提（ヒアリング結果）:

| 項目 | 決定 |
|---|---|
| 形態 | Web アプリ |
| MVP の優先軸 | ドリル体験の質（出題アルゴリズムとコンテンツ） |
| 科目の広げ方 | 算数を土台に、暗記系（漢字・英単語）へ横展開 |
| 進め方 | 設計書 → 実装 |

## 1. 現状評価

### 1.1 引き継ぐ価値のある資産

- **`core/` が純関数として分離されている** — `problems` / `difficulty` / `planning` / `combo` は I/O に依存せず、テストも書かれている。Web 版でもドメイン層としてほぼそのまま移植できる。
- **grow / fun の二軸というプロダクト仮説** — 「伸ばすモード」と「楽しさに気づくモード」の分離は、他の学習アプリにない明確な差別化になりうる。ここは設計の中心に据える。
- **決定論的な問題生成**（`(level, seed)` → 同一問題）— 再現性があり、テスト・リプレイ・複数端末同期のいずれにも効く。良い設計判断。
- CI・型注釈・docstring・pytest が揃っており、土台の作法は既にできている。

### 1.2 実用化の前に潰すべき問題

#### ★ 重大バグ: 難易度が1セッションで振り切れる

`cli.py::_run_grow_session` は **1問ごとに** `adjust_difficulty` を直近10問の窓で呼ぶ。
レベルが変わっても窓がリセットされないため、同じ判定が連続発火する。シミュレーション結果:

```
実力90%の子のレベル推移（30問）
[2, 3, 4, 5, 6, 7, 8, 9, 10, 10, 10, ...]   ← 9問で最大レベルに到達

実力50%の子のレベル推移（30問）
[2, 1, 1, 1, ..., 1, 2, 3]                  ← 底に張り付いた後に突然上昇
```

`adjust_difficulty` 自体は正しい。**呼び出し側の設計が誤っている**（純関数を「状態遷移」として使ってしまっている）。
Web 版ではこの1次元レベル方式そのものを Elo 方式に置き換えることで根本解決する（§5）。

#### その他の構造的な制約

| # | 問題 | 影響 |
|---|---|---|
| 1 | `completed_pages` が常に 0 で呼ばれ、進捗を記録するコマンドが存在しない | 「日割りノルマ」が初日から変化せず、計画機能が実質的に動いていない |
| 2 | 児童名が主キー（`children: dict[str, ChildData]`） | 同名の子で衝突。改名で履歴消失 |
| 3 | 難易度レベルに「演算子」と「数値範囲」が癒着 | 学年別カリキュラム（分数、単位、文章題）へ拡張できない |
| 4 | 解答は `int` のみ | 分数・小数・漢字・英単語を表現できない |
| 5 | 解答時間を記録していない | 適応出題の情報量が半分。「解けたが遅い」＝未定着を検出できない |
| 6 | fun モードが固定 Lv.2、コンボがセッションを跨いで残らない | 継続動機の設計として弱い |
| 7 | `~/.drillnavi/data.json` 単一ファイル | 複数端末・複数ユーザー・同時アクセス不可 |
| 8 | 「同じ問題をいつ再出題するか」の概念がない | 暗記系（漢字・英単語）へ横展開できない |

## 2. プロダクト定義

### 2.1 誰の何を解決するか

> **メインターゲット: 勉強を後回しにする子（小学3年〜中学生）と、その子を毎日見ている学童スタッフ・保護者。**

この層が既存サービス（スタサプ等）で続かない理由は、コンテンツの質ではなく **「何を、どれだけ、いつやるか」の判断コストを子どもに丸投げしている** こと。
DrillNavi は「今日やる分」を1画面に確定させ、迷いをゼロにする。

| ペルソナ | 状況 | DrillNavi が返すもの |
|---|---|---|
| **たろう（小4・後回し型）** | 夏休みの宿題が8月末に全部残る。机に向かうまでが長い | fun モードで3分。「今日やる分」が3問だけ表示され、始める心理的コストが下がる |
| **はなこ（小6・まじめ型）** | 毎日やるが、できる問題を繰り返して時間を浪費 | grow モードが正答率75%になる難易度を自動で当て、同じ時間で伸びる量を増やす |
| **佐藤さん（学童スタッフ）** | 15人を1人で見る。誰が詰まっているか分からない | ダッシュボードで「今日手をかけるべき3人」が上に出る |
| **保護者** | 進捗を知りたいが管理はしたくない | 週1のレポート（現行 PDF 機能の発展形） |

### 2.2 二つのモードの再定義

現行実装では「fun = 易しい問題」という差しかない。実用版では**目的関数そのものを変える**。

| | **grow モード** | **fun モード** |
|---|---|---|
| 目的 | 学力の伸長 | 学習行動の着火・習慣化 |
| 目標正答率 | **75%**（適応学習研究で動機と学習効率が両立する水準） | **85〜90%**（成功体験を優先） |
| 出題方針 | Elo で能力に最も近い難易度を選ぶ。未定着項目を優先 | 既習・定着済みから出す。テンポ重視 |
| 1セッション | 10〜15問 / 10分 | **5問 / 3分**（「これだけ？」と思わせる） |
| セッション終了 | 到達度サマリと弱点3つ | コンボ・称号・演出 |
| 誰が選ぶか | 子ども自身、または AI が「今日は fun」と提案 | 同左 |

**設計の肝**: 連続未実施が3日を超えたら、アプリ側が自動で fun モードを提案する。
「勉強しない子」に対しては、正しい問題を出すことより **戻ってこさせること** の優先度が高い。

## 3. スコープとロードマップ

段階ごとに「誰かに使ってもらえる状態」で切る。

### Phase 1 — 動くドリル（4〜6週）★ 今回の MVP

- Web アプリ（ログイン、子ども1人、grow / fun）
- 算数コンテンツ: 小3〜小6の四則演算・分数・小数（テンプレート方式で 40〜60 種）
- Elo による適応出題（§5.1）
- 解答時間の記録
- セッション終了サマリ
- **完了条件: 学童の子ども3人に1週間使ってもらい、離脱ポイントを観察できる**

### Phase 2 — 続く仕組み（+3週）

- 連続日数・スタンプ・称号の永続化
- 「今日やる分」ホーム画面（計画機能の作り直し、進捗記録を含む）
- 週次レポート（現行 PDF 機能の Web 化）

### Phase 3 — 暗記系へ横展開（+4週）

- FSRS による間隔反復（§5.2）
- 漢字（小学校配当漢字1026字）・英単語
- 解答形式の抽象化（数値 / 選択 / テキスト / 手書き）

### Phase 4 — 他者に提供する（+4週）

- 指導者ダッシュボード（複数の子を一覧）
- 教室単位のアカウント管理、招待フロー
- 個人情報の取り扱い整備（§8）

### スコープ外（当面やらない）

- 動画講義（スタサプの土俵で戦わない）
- ネイティブアプリ（Web で PWA として自宅画面に置ければ十分）
- 独自の AI 質問応答（コストとハルシネーションのリスクが Phase 1 に見合わない）

```
┌──────────────────▼──────────────────────┐
│  バックエンド  FastAPI (Python 3.12)
│  ┌───────────────────────────────────┐
│  │ api/       ルーティング・認証・DTO      │
│  ├───────────────────────────────────┤
│  │ core/      ★純粋ドメイン層（現行から移植）│
│  │   problems / difficulty(Elo) /       │
│  │   scheduling(FSRS) / planning / combo │
│  ├───────────────────────────────────┤
│  │ repository/ SQLAlchemy               │
│  └───────────────────────────────────┘
└──────────────────┬──────────────────────┘
                   │

```

**なぜ Python を残すか**: `core/` の純関数群とテストがそのまま活きる。加えて Elo / FSRS の数値検証やシミュレーション（既にある `experiments/sim_adaptive.py` の発展形）を同じ言語で回せる。
**なぜ全部 Next.js にしないか**: 出題アルゴリズムは今後もオフラインでのパラメータ最適化が必要で、Python の方が有利。

**設計原則**: `core/` は DB もネットワークも知らない純関数のまま維持する。現行コードの最大の美点であり、アルゴリズムを差し替えながら検証するために必須。

## 5. 出題アルゴリズム

現行の「1次元レベル 1〜10」を捨て、**2つの独立した問い**に分解する。

> **A. 今この瞬間、どの難易度の問題を出すか** → Elo（§5.1）
> **B. 一度やった項目を、いつ再び出すか** → FSRS（§5.2）

A は算数（grow）の中核、B は暗記系（Phase 3）の中核。両方を同じ出題キューに統合する。

### 5.1 Elo レーティングによる適応出題

生徒の1回の解答を「生徒 vs 問題」の1試合とみなす。教育分野で広く検証された手法。

```
生徒の能力         θ  （スキルごとに保持）
問題の難易度       β  （項目ごとに保持）
正答確率の予測     P = 1 / (1 + exp(-(θ - β)))
更新               θ ← θ + K_s (result - P)
                   β ← β - K_i (result - P)
```

**現行方式に対する優位点**

| | 現行（±1レベル） | Elo |
|---|---|---|
| 振れ幅 | 判定ごとに固定1段階 → 暴走 | 予測との乖離に比例 → 自己安定 |
| 問題の難易度 | 人間が決め打ち | 実データから自動推定 |
| 目標正答率 | しきい値を跨ぐと必ず動く | 予測確率 0.75 の問題を選ぶだけ |
| 初見の子 | Lv.1 から手探り | 学年から事前分布を置ける |

**採用する拡張**

1. **不確実性ベースの K 値** — 解答数が少ないうちは K を大きく（速く収束）、増えたら小さく（安定）。
   `K = a / (1 + b·n)`（n = 解答数、a≈0.6, b≈0.05 を初期値として実データで調整）
2. **解答時間の利用** — 正解でも標準時間の2倍以上かかった場合は「未定着」として θ の上昇を割り引く。
3. **スキル分解** — θ を単一値でなく **KC（Knowledge Component）ごと**に持つ。
   例: `繰り上がりのある足し算` / `2桁×1桁の掛け算` / `分母が異なる分数の足し算`。
   「掛け算はできるが繰り下がりが苦手」を検出でき、これがそのまま指導者向けの弱点レポートになる。
4. **出題選択** — 予測正答率が目標に最も近い項目を選ぶが、**決定論にしない**。
   目標周辺（grow: 0.65〜0.85 / fun: 0.80〜0.95）から重み付きランダムに選ぶ。毎回同種の問題が出ると飽きるため。

### 5.2 FSRS による間隔反復（Phase 3）

暗記系では「難易度を合わせる」より「忘れる直前に出す」が効く。
FSRS-6 は約7億件のレビュー履歴で学習された現行の標準アルゴリズムで、SM-2 比で同じ定着度を **20〜30% 少ない復習回数**で達成する。

- 項目ごとに **安定度 S / 難易度 D / 想起確率 R** を保持
- 目標保持率（例 0.90）を下回る日を次回出題日とする
- 既存の OSS 実装（`fsrs` Python パッケージ）を使い、自前実装しない

**算数にも部分的に適用する**: 一度定着した KC も放置すれば忘れる。grow セッションの2割を「復習枠」として FSRS から供給する。

### 5.3 統合出題キュー

1セッションの構成比（grow モード・10問の例）:

```
 復習枠（FSRS が今日と判定）      2問  ← 定着の維持
 適応枠（Elo で P≈0.75）          6問  ← 伸長の本体
 挑戦枠（Elo で P≈0.5）           1問  ← 天井を上げる／飽き防止
 確実枠（Elo で P≈0.95）          1問  ← セッション最後に置き、成功で終わらせる
```

**最後を必ず正解で終える**のは意図的な設計。次回の着席率に効く。

## 6. データモデル

現行 JSON からの主な変更: **ID 主キー化 / 項目の抽象化 / 解答時間の記録 / KC の導入**。

```
Organization (教室)
  └ User (指導者・保護者)        role, email
  └ Learner (学習者)             id(UUID), display_name, grade, birth_year
       ├ SkillState              learner_id, kc_id, theta, n_attempts, updated_at
       ├ CardState               learner_id, item_id, stability, difficulty, due_at
       ├ Attempt                 learner_id, item_id, is_correct,
       │                         elapsed_ms, given_answer, mode, answered_at
       ├ Plan                    subject, total_units, completed_units, due   ← 進捗を持つ
       └ StreakState             current_streak, longest_streak, last_active_on

KnowledgeComponent (KC)          id, subject, grade, name, parent_id
  └ ItemTemplate                 id, kc_id, generator_key, answer_type, beta(難易度)
       └ (Item は template + seed から決定論的に生成。実体を保存しない)
```

**設計上の要点**

- **`Item` を DB に持たない** — `(template_id, seed)` から決定論的に再生成する現行の思想を維持。数百万件の問題テーブルを持たずに済み、リプレイも可能。ただし `beta` はテンプレート単位で保持する。
- **`answer_type` で解答形式を抽象化** — `integer` / `fraction` / `decimal` / `choice` / `text` / `kanji`。これが暗記系への横展開の鍵。現行の `answer: int` 固定を最初に壊す。
- **`Attempt` は追記のみ（イベントソーシング）** — θ も streak もすべて Attempt から再計算可能にする。アルゴリズムを変えたとき、過去データで再評価できる。これは実用アプリでは死活的に重要。
- **`Plan.completed_units`** — 現行の未実装部分。ドリル完了時に自動加算する。

## 7. コンテンツ設計

### 7.1 算数（Phase 1）

現行の「レベル→数値範囲」を、**学習指導要領に沿った KC ツリー**に置き換える。

```
算数
├ 数と計算
│   ├ 小1: 繰り上がりのない足し算 / 繰り上がりのある足し算 / ...
│   ├ 小3: 2桁×1桁の掛け算 / あまりのある割り算 / ...
│   ├ 小5: 通分をともなう分数の足し算 / 小数の掛け算 / ...
├ 図形
├ 測定・単位
└ 文章題（Phase 2 以降）
```

各 KC に `ItemTemplate` を 3〜5 個ぶら下げ、**Phase 1 で計 40〜60 テンプレート**。
テンプレートはパラメータ生成器（現行 `generate_problem` の一般化）として実装する。

### 7.2 暗記系への横展開（Phase 3）

| 科目 | データ源 | 出題形式 |
|---|---|---|
| 漢字 | 学年別漢字配当表（1026字・公開データ） | 読み（選択/テキスト）→ 書き（手書き認識は後回し、まず選択式） |
| 英単語 | 小中学校の基本語彙リスト | 日→英 / 英→日 / 音声 |

**横展開が低コストで済む理由**: §6 の `answer_type` 抽象化と §5.2 の FSRS を Phase 1・3 で先に入れておくため、
漢字の追加は「KC ツリーとテンプレートを足すだけ」になる。アルゴリズムには一切手を入れない。

## 8. 継続の仕組み（Phase 2）

「勉強しない子」がメインターゲットである以上、ここは付属機能ではなく**主機能**。

- **連続日数（streak）** — ただし途切れたときのダメージを設計する。「1日休んでも streak を守れる回復チケット」を週1枚配る。途切れた瞬間に離脱するのを防ぐ。
- **今日やる分を1つに絞る** — ホーム画面に選択肢を並べない。ボタンは「はじめる」1つ。
- **3分で終わる** — fun モードは5問。「思ったより早く終わった」体験が翌日の着席につながる。
- **成長の可視化** — 正答率ではなく「解けるようになった KC 数」で見せる。正答率は目標75%に張り付くので、伸びの実感には使えない。
- **通知は保護者経由** — 子ども端末への直接プッシュは避け、保護者/指導者に「今日まだの子」を通知する。

## 9. 非機能要件

### 9.1 個人情報（他者提供を前提とするため必須）

- 学習者は**氏名を必須にしない**。表示名（ニックネーム）＋ 教室内の整理番号で運用可能にする。
- 収集する個人情報は「学年」「表示名」「学習履歴」に限定。生年月日は年のみ。
- 16歳未満のデータ取得には保護者同意が必要（個人情報保護法）。教室契約時に同意取得フローを設ける。
- データ削除（退会時の完全削除）と、エクスポート（他サービスへの持ち出し）に対応する。
- 学童・塾に提供する場合、事業者との間で**委託契約と安全管理措置の取り決め**が必要になる。
  ※ ここは法的助言ではなく論点の整理。実際に外部提供する段階で専門家の確認を推奨。

### 9.2 その他

- **アクセシビリティ**: 小学校低学年が読めるフォントサイズ（最小 18px）、ふりがな切替、色覚多様性に配慮した配色。
- **オフライン**: PWA で 1セッション分を先読みキャッシュ。学童の Wi-Fi は不安定であることが多い。
- **入力**: 数値入力は OS のキーボードではなく**アプリ内テンキー**。タブレットでの誤爆を防ぐ。
- **パフォーマンス**: 問題表示は 100ms 以内。ここが遅いとテンポが死に、fun モードの価値が消える。

## 10. 既存コードからの移行方針

| 現行ファイル | 扱い |
|---|---|
| `core/problems.py` | **拡張して移植**。`generate_problem(level, seed)` → `generate(template_id, seed)` に一般化。決定論の思想は維持 |
| `core/difficulty.py` | **置き換え**。`core/elo.py` を新設。ただし既存テストは「回帰の基準」として残し、新旧を並走比較する |
| `core/planning.py` | **ほぼそのまま移植**。`completed_pages` を実際に渡す呼び出し側を作る |
| `core/combo.py` | **そのまま移植**。永続化層を追加 |
